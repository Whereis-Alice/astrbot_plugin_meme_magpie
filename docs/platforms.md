# 平台与协议端支持

> [← 返回 README](../README.md) · [文档目录](README.md) · [English](en/platforms.md)

插件本身跨平台，图片收发在哪个平台都能用。需要特殊处理的是 **QQ 商城表情**（那些要下载才能用的付费表情包）——它在各家 OneBot 协议端里的传法完全不一样，这块专门做了适配：

| 协议端 | 商城表情怎么传 | 表情标记字段 | `summary` 外显 |
|:---|:---|:---|:---|
| **LLBot** | 独立的 `mface` 段，AstrBot 不会把它转成图片组件 | 只有 `subType`（驼峰） | 不发 |
| **NapCat** | 折进普通 `image` 段，连 `sub_type` 键都没有 | 只有 `sub_type`（下划线） | 常为空 |
| **SnowLuma** | 折进普通 `image` 段，且 `sub_type` 是 `0` | 只有 `sub_type` | 一定有 |

对应的处理是：

- **收图**：商城表情直接从 OneBot 原始消息段里读，不依赖 AstrBot 的图片组件（否则 LLBot 的 `mface` 会整段丢失）。判断「这是表情不是普通图」除了看 `sub_type` / `subType` / `summary`，还会看 `emoji_id`、`emoji_package_id`、`key` 这些商城专属字段——SnowLuma 的 `sub_type: 0` 就是靠这一层兜住的。入库时顺带记下 `emoji_id`、表情包 id 和外显名，方便回溯来源。
- **发图**：以「表情」形式发出去时，`summary`、`sub_type`、`subType` 三个键一起写，谁认哪个都能正确渲染成表情，多余的键各家都会忽略。

前提是 OneBot 的 `messageFormat` 用 `array`（默认值）。如果你把它改成了 `string`，原始消息会变成一段 CQ 码字符串，商城表情就读不出来了。

其它平台（Telegram、QQ 官方机器人）按普通图片处理，功能不受影响。QQ 官方机器人没有 OneBot 的表情标记，另有「表情收录模式（QQ_Official）」这个配置项决定收哪些图。

## 和分段回复插件配合

装了 [astrbot_plugin_outputpro_split](https://github.com/Whereis-Alice/astrbot_plugin_outputpro_split) 这类「把一条长回复拆成几条发」的插件时，本插件的表情包默认是**另一条独立消息**，对方看不见它，也就没法按自己的图片 / 表情策略排版。把「自动表情的投递方式」改成 `attach` 即可解决：

| 取值 | 行为 | 适合 |
|:---|:---|:---|
| `separate`（默认） | 表情单独发一条消息，与以往行为完全一致 | 没装分段回复插件，或只想要最稳的兼容性 |
| `attach` | 表情追加到机器人这条回复的消息链末尾 | 想让分段回复插件把文字和表情一起编排 |

`attach` 的代价是选图必须在回复发出前完成，所以回复会稍慢一点。为此有一道超时（默认 10 秒）：超时、选不出图、任何一步失败都会自动回退成 `separate` 异步补发——**回复本身不会被卡住，最坏情况只是表情来晚一点**。另外，这条回复要被转成长图（AstrBot 的文本转图片）时 `attach` 会自动让位，否则挂在链尾的表情会被一起画进图里。

### 那个「兼容路径」开关是干什么的

`outputpro_split` 判断「这张图是表情包」的方式，是看图片路径里有没有 `plugin_stealer` 字样——那是原插件的目录名，本插件换了包名，自然就对不上了。

打开「为分段回复插件生成兼容路径」后，要附加的表情会先硬链接（同盘失败则复制）到一个名字含该字样的兼容目录，再附加进消息链，这样对方就能正确识别成表情。原图和库里记录的路径都不动，兼容目录只保留最近 64 个文件，磁盘占用可以忽略。

这是个权宜之计：更干净的做法是请上游把 `astrbot_plugin_meme_magpie` 也加进它的识别关键字，到那时把这个开关关掉就行。
