## 这是什么

喜鹊自古是出名的贼鸟，看到亮闪闪的东西就往窝里叼。这个插件干的是同一件事——群里刷过的表情包，它顺手偷进图库，用视觉模型看懂「这张图在表达什么」，分类、打标签、抄下图上的字，然后在 Bot 回复时挑一张情绪对得上的发出去。

三件事各自独立开关，互不影响：

- **收**：监听聊天里的图片，按概率或冷却收进「待审核池」，你在 WebUI 点通过才正式入库。
- **认**：视觉模型（VLM）识别分类、标签、使用场景、图上文字、角色和作品。
- **发**：Bot 回复后按概率决定要不要配一张表情包；选哪张走语义检索 + 情绪匹配。

不想让它继续收了就 `/mp off`，已经进库的表情包照样能发。

### 关于名字

对外的名字是 **meme神偷**（英文 Meme Thief），指令组是 `mp`——meme + pilfer，两个字母好敲。

1.0 时期叫「表情包喜鹊」，所以旧的 `magpie` 和中文 `神偷` 都保留成别名，三种写法完全等价：

```
/mp status
/magpie status
/神偷 status
```

仓库名和 Python 包名仍然是 `astrbot_plugin_meme_magpie`，这个是**故意不改**的：AstrBot 拿 `metadata.yaml` 里的 `name` 当插件目录名，同时也当数据目录 `data/plugin_data/<name>`。改掉它等于让所有老用户的表情包和数据库「凭空失踪」，所以这一层保持原样。

### 和 astrbot_plugin_stealer 的关系

本插件基于 [nagatoquin33/astrbot_plugin_stealer](https://github.com/nagatoquin33/astrbot_plugin_stealer) 二次开发（AGPL-3.0），感谢原作者把这套玩法做出来。

它是一个**完全独立的插件**：包名、命令前缀、数据目录、WebUI 路由、LLM 工具名都换过了，可以和原插件装在同一个 AstrBot 里共存，不会互相覆盖数据。如果你原来在用 stealer，一条 `/mp migrate apply` 就能把表情包和数据库搬过来，旧数据默认原样保留。

相比原插件，这一版主要多了这些东西：

| 改动 | 说明 |
|:---|:---|
| **数据迁移指令** | `/mp migrate` 一条指令搬走旧插件的图片、数据库、分类、角色库、黑名单和配置 |
| **LLM 直接传参入库** | LLM 主动收图时可以顺手写清「这是哪个作品的哪个角色、在做什么」，不再只靠视觉模型猜 |
| **批量识别限流** | 批量导入 / 批量重新识别可设并发数与每分钟请求上限，几百张图也不会打爆上游触发 429 |
| **作品维度** | 新增「作品名」字段，从入库、检索一路贯通到 WebUI 筛选 |
| **批量重新识别** | 对已入库但缺标签 / 缺描述的老图重跑视觉识别，可选只补空、不覆盖已有内容 |
| **识别时带上已知信息** | 已经填好的作品 / 角色会写进识别提示词，模型直接采用而不是重新猜，二次元图提升最明显 |
| **待审核池重新识别** | 审核区的图也能批量重跑识别，而且会直接修正分类 |
| **识别失败检测** | 一键列出描述为空的条目，逐张补写或整批重跑，失败的图不再淹没在图库里 |
| **多协议端适配** | LLBot / NapCat / SnowLuma 在商城表情和表情外显上的差异全部兜住 |
| **分段回复插件兼容** | 新增 `attach` 投递模式，表情可以并进本条回复的消息链 |
| **若干上游 Bug 修复** | 见下文[修了哪些问题](#修了哪些问题) |

## 核心功能

| 功能 | 说明 |
|:---|:---|
| **自动收集** | 监听聊天图片，概率 / 冷却两种模式；QQ 官方机器人平台有专门的表情识别策略 |
| **待审核池** | 自动收来的图先进审核区，人工点通过才入库，避免图库被随手截图污染 |
| **视觉识别** | VLM 输出结构化 JSON：分类、标签（0~3 个）、使用场景（1~2 个）、图上文字、情绪 |
| **语义检索** | 图上文字 + 使用场景 + 文本嵌入向量匹配；分类只加分不硬过滤；嵌入不可用时自动降级 BM25 |
| **情绪匹配** | 从 Bot 回复中提取检索词和情绪先验，挑一张对得上的，不改动 LLM 原本的回复内容 |
| **LLM 主动用图** | 对话中 LLM 可以自己检索、发送、收录表情包 |
| **角色与作品库** | 手工归档「这是谁 / 出自哪部作品」，和情绪分类相互独立 |
| **WebUI 管理面板** | 审核区 + 图库双区：浏览、编辑、排序、批量操作、批量导入、批量重新识别、识别失败检测、存储清理 |
| **群聊过滤** | 收和发各有独立黑白名单，支持 `group:群号` 和 `user:QQ号` |
| **重复图清理** | 感知哈希（pHash）找出内容重复的图 |
| **多语言界面** | 中文 / English / Русский |
| **商城表情** | QQ 付费商城表情（`mface`）也能收，LLBot / NapCat / SnowLuma 三家协议端都适配 |
| **分段回复兼容** | 可把表情并进机器人这条回复的消息链，让 outputpro_split 这类插件统一编排 |

## 快速开始

### 1. 先配好视觉模型

插件靠 VLM 读懂图片，**没有视觉模型基本等于不能用**。两种配法任选其一：

- 在 AstrBot 后台配好「图片描述模型」，插件会自动拿来用；
- 或者在插件配置里单独指定「视觉模型」（`vision_provider_id`）。

嵌入模型（Embedding）是可选项：配了检索更准，没配会自动降级成 BM25 关键词检索，功能不受影响。

### 2. 安装

在 AstrBot 插件市场搜索 `astrbot_plugin_meme_magpie`，或者在插件管理页面用仓库地址安装：

```
https://github.com/Whereis-Alice/astrbot_plugin_meme_magpie
```

### 3. 三条命令跑起来

```
/mp on        # 开始收表情包
/mp auto_on   # 开启聊天时自动发表情包
/mp status    # 看看现在收了多少
```

> **关于 `/` 这个前缀**：`/` 只是 AstrBot 的出厂默认唤醒前缀，你可以在 AstrBot 设置里把它改成 `!`、`#`、`.`，也可以整个清空（清空后直接发 `mp status`）。本文档一律按默认的 `/` 书写，请自行替换成你实际用的那个。私聊或者 @机器人 的场合本来就不需要前缀。
>
> 不确定自己的前缀是哪个？插件所有回复里的命令示例都会按**你实际生效的前缀**渲染，照抄回复里的写法就行；发一次 `/mp help` 可以打印完整的子命令清单。

### 4. 打开管理面板

AstrBot 插件详情页 →「表情神偷管理面板」。不用额外开端口，不用另设密码。

## 从原插件迁移数据

`/mp migrate` 用来把 `astrbot_plugin_stealer` 的数据搬到本插件。整个过程是**幂等的**（重复执行不会重复导入）、**非破坏性的**（默认复制文件，旧插件数据原样保留），可以放心先试。

推荐三步走：

```
/mp migrate check     # 第一步：看看能不能找到旧插件的数据目录
/mp migrate           # 第二步：预演，只打印「如果执行会发生什么」，一个字节都不写
/mp migrate apply     # 第三步：真的搬（复制文件，旧数据保留）
```

磁盘紧张、不想留两份图片的话，用 `/mp migrate move` 代替 `apply`——它移动而不是复制文件，**执行后旧插件就不可用了**，请先用前两步确认无误。

自动找不到旧目录时，手动把路径给它：

```
/mp migrate apply D:/astrbot/data/plugin_data/astrbot_plugin_stealer
```

**会搬的东西**

- `categories/` 下所有分类图片、`pending/` 待审核图片、`raw/` 暂存图片
- 数据库里的表情包记录：分类、标签、场景、描述、情绪、使用次数、作用域、来源、入库方式等
- 待审核池记录、去重黑名单
- `categories.json` / `category_info.json` / `characters.json` / `character_info.json`
- 旧插件的配置项（只搬本插件也有的键，本插件新增的配置保持默认值）

**不会搬的东西**：缩略图缓存、临时文件、语义向量。语义向量会在插件启动时自动按需补齐，你不用做任何事；只有索引本身出问题（图片在、但列表里搜不到）才需要跑一次 `/mp rebuild_index`，它只重建索引，**不会删图**。

迁移完先去看一眼「最大表情包数量」够不够大——搬进来几百张、上限却还是个小数字的话，超出的部分会被算作溢出。默认值 `2000`，而且默认只告警不删，详见[表情库容量上限](#表情库容量上限)。

迁移结束会打印一份报告：搬了多少张图、跳过多少张（已存在 / 文件缺失 / 哈希重复）、失败多少张。文件名撞车时自动改名，绝不覆盖已有的图。

## LLM 主动用图

对话中 LLM 可以自己调三个工具，不需要你下指令：

| 工具 | 作用 |
|:---|:---|
| `magpie_search_meme` | 检索候选表情包，返回分类、作品、角色、场景、作用域、使用次数等参考信息 |
| `magpie_send_meme` | 从候选里挑一张发出去；发送失败会返回明确原因，方便 LLM 重选 |
| `magpie_steal_meme` | 把当前消息里的图片收进库；`image_ref` 留空则自动取第一张图 |

### 让 LLM 自己填元数据

视觉模型认不出「这是《孤独摇滚》里的后藤一里在抱头」这种二次元细节，是这类插件最常见的翻车点。所以 `magpie_steal_meme` 开放了参数，让**聊天中的 LLM 把它已经知道的信息直接写进库**：

| 参数 | 说明 |
|:---|:---|
| `work` | 作品名，比如「孤独摇滚」「原神」 |
| `character` | 角色名，比如「后藤一里」 |
| `action` | 图里在做什么动作，比如「抱头」「捂脸」 |
| `desc` | 一句话描述这张图 |
| `tags` | 关键词标签，逗号或顿号分隔 |
| `scenes` | 适合什么场景用，逗号或顿号分隔 |
| `emotions` | 情绪词，逗号或顿号分隔 |
| `overlay_text` | 图上写的字 |
| `category` | 指定分类（必须是已有分类名，非法值会被忽略并回退） |

参数全填、填一半、一个都不填都可以，缺的部分继续交给视觉模型补。用法举例——你在群里说：

> 把这张图偷了，这是孤独摇滚的波奇酱，在抱头尖叫

LLM 就会带着 `work="孤独摇滚"`、`character="后藤一里"`、`action="抱头尖叫"` 调用工具，入库质量比纯靠视觉模型高一个档次。

三种采纳策略由配置项**「LLM 偷图参数采纳策略」**（`llm_steal_param_mode`）决定：

| 取值 | 行为 | 适合 |
|:---|:---|:---|
| `merge`（默认） | LLM 给的字段优先，没给的用 VLM 分析结果补 | 绝大多数情况 |
| `llm_first` | LLM 给齐了关键字段就**跳过 VLM 调用**，省一次请求 | 想省 Token，且信任对话模型 |
| `vlm_only` | 忽略 LLM 传的参数，只用 VLM 分析 | 想完全交给视觉模型 |

无论哪种策略，**内容审核始终在最前面执行，LLM 无法绕过**。

### 已知信息会写进识别提示词

填好的信息不只是存进数据库，还会写进视觉模型的提示词。识别请求里会多出这样一段：

```
<known_facts>
以下信息由用户或上层对话模型提供，已确认可信，请直接采用，不要推翻或改写：
- 作品：孤独摇滚
- 角色：后藤一里
- 动作：抱头尖叫
description 与 scenes 要把上面给出的信息用进去，不要另起一套说法。
tags 只补充上面没提到的画面关键词。
</known_facts>
```

模型不用再把力气花在猜「这是谁」上，而是照着已知信息写描述和适用场景。三处入口都接上了：

- **LLM 主动收图**：LLM 传的 `work` / `character` / `action` / `overlay_text`
- **WebUI 单张识别**：弹窗里填过的作品 / 角色会自动带上
- **批量重新识别**：每张图自动沿用库里已填的作品 / 角色，不让模型重新猜它本来就知道的事

想清掉某条线索，把对应字段留空提交即可。识别缓存会按已知信息分桶，带线索和不带线索的结果不会互相污染；用自定义提示词覆盖了内置模板也不影响这项能力（模板里缺 `{known_facts}` 占位符时会自动插到合适位置）。

## 批量导入与批量重新识别

两个功能都在 WebUI 图库页，都受同一套限流器管理。

### 批量导入

一次上传几十上百张图，两种模式互斥：

- **指定分类**：直接存进你选的分类，不调用视觉模型，速度最快；
- **自动识别**：不选分类，由 VLM 逐张识别分类和标签。

导入前还可以统一填「角色」和「作品」，省得一张张改。

### 批量重新识别

给已经在库里的老图重跑视觉识别，适合两种场景：早期入库的图没标签、或者换了更好的视觉模型想重新标一遍。

- **范围**：勾选的图片 / 缺标签或缺描述的图片 / 只补没有描述的 / 全部图片
- **覆盖已有内容**：默认关闭，只往空字段里填，不动你手工写过的描述和标签
- **数量上限**：可以限制这一批最多处理多少张，先小范围试水
- 出于安全考虑，重新识别**不会自动改分类**（改分类要移动文件，并发下风险高），只在结果里给出「建议分类」，你自己决定要不要改

**审核区也能重新识别**：待审核池的图同样支持批量或单张重跑，范围一样是「勾选的 / 缺标签的 / 全部」。和图库唯一的区别是**待审核记录的分类会被直接修正**——它只是数据库里的一个字段，改它不需要移动文件；正式库的分类对应真实目录，所以那边仍然只给建议。

### 挑出识别失败的图

识别偶尔会失败——超时、被上游限流、模型返回空内容，都会留下一条「有图但没描述」的记录。描述是搜索的主要依据，空着这张图基本就搜不出来了。

图库和审核区的工具栏各有一个「识别失败」按钮，点开会列出所有描述为空、也就是列表里显示「暂无描述」的条目。每一条有三种处理方式：

- 自己写一句描述，点「仅保存」；
- 点「识别这张」只重跑这一张——**识别结果先填进输入框**，你确认无误再保存，不会背着你写库；
- 或者一键把这一批交给「批量重新识别」，几百张一次跑完。

待审核池条目特别多时只会检查最新的一批，弹窗里会写清本次检查了多少条，处理完再打开会接着往下检查。

### 怎么设并发和速率才不会被 429

限流器做了三件事：**并发上限**（同时在飞的请求数）、**RPM 令牌桶**（平均每分钟请求数）、**退避重试**（遇到 429 / 5xx / 超时自动等待重试，并把整条队列一起推后，避免几个 worker 前后脚接着撞墙）。

弹窗里的「并发」和「速率」是**这一次任务的临时值**，改了不影响插件配置；插件配置里的值是每次打开弹窗的默认值。

按上游额度对着填就行：

| 你的情况 | 并发 | 每分钟上限（RPM） |
|:---|:---:|:---:|
| 免费 / 试用额度，只知道很容易 429 | 1 | 6 ~ 10 |
| 常见付费 API（OpenAI、通义、智谱等入门档） | 2 ~ 3 | 20 ~ 60 |
| 高配额或自建推理服务 | 4 ~ 8 | 120 ~ 300 |
| 完全不想限速（本地模型） | 8 ~ 16 | 0（0 = 不限速，只受并发约束） |

不确定的话就用默认的「并发 2 + RPM 20」，几百张图大约一小时内跑完，基本不会触发限流。任务里如果被限流了，进度条上的「限流次数」和「重试次数」会实时涨，看到它涨就该往下调。

其余两项在插件配置里（`batch_analyze_max_retries` 重试次数，默认 3；`batch_analyze_retry_backoff` 退避基数，默认 2.0，即 1s → 2s → 4s 递增，带随机抖动）。上游返回了 `Retry-After` 头时会优先听它的。额度耗尽、Key 无效、鉴权失败这类**不可能重试成功**的错误会直接失败，不浪费额度。

### 进度显示

任务跑起来之后，进度面板会显示：

- 进度条 + 「已处理 / 总数」，暂停时进度条变色
- 当前正在处理的文件名和阶段（识别中 / 入库中）
- 成功 / 失败 / 已识别 / 限流次数 / 重试次数
- 预计剩余时间（按实际速率动态估算）
- 失败明细：哪张图失败了、失败原因
- 重新识别任务还会额外给出「改动了多少字段」和「建议改分类的图片列表」

任务可以随时**暂停 / 继续 / 取消**，暂停是真的把 worker 停住，不是只停 UI。关掉浏览器标签页任务照样在后台跑，重新打开面板会自动接回进度。

指令组是 `mp`，别名 `magpie` 和 `神偷`。下表只写子命令，实际发送时记得带上你的唤醒前缀，例如 `/mp status`（默认前缀）或 `!mp status`（把前缀改成 `!` 的情况）。

### 表情库容量上限

这是插件里唯一一个会**主动删你数据**的机制，单独讲清楚：

- **在哪里改**：AstrBot 插件配置页**最上面**那个分组「=== 容量与安全（重要）===」，第一项就是「最大表情包数量」。（1.4.1 之前它排在第 46 项，得翻到最底下才看得见，所以搬上来了。）
- 「最大表情包数量」是硬上限。超出时从最旧的开始删，**图片文件一起删，删掉找不回来**（标记为收藏的不参与）。
- 默认 `2000`，够绝大多数人用。填 `0` 表示不限制，只受磁盘大小约束。
- 默认**不会自动删**：超出上限时只在日志里写一条告警（搜关键字「容量控制」能找到），告诉你现在多少张、超了几张。要清理请手动 `/mp capacity`；想让它每小时自动清，打开「容量超限自动清理」。
- 插件启动时也会检查一次，超了就直接在日志里说清楚（只告警，不删）。
- `/mp status` 只读数字不删东西，`/mp capacity` 才会真的删。

> **1.3.0 及更早版本这一项默认只有 `100`**，而且后台巡检会自动删、`/mp rebuild_index` 也会顺手删。如果你在旧版遇到过「表情包莫名少了几十张」，基本就是这里——去日志里搜「容量控制」就能确认。1.4.0 起默认值提到 2000，并且默认只告警不删。
>
> ⚠️ **注意：默认值提高不会改写你已经保存过的配置。** AstrBot 只给缺失的配置项填默认值，你的配置文件里已经存着 `100` 的话，升级后它还是 `100`。所以从 1.3.x 升上来的话，请去配置页顶部亲眼确认一次这个数字。

## 平台与协议端支持

插件本身跨平台，图片收发在哪个平台都能用。需要特殊处理的是 **QQ 商城表情**（那些要下载才能用的付费表情包）——它在各家 OneBot 协议端里的传法完全不一样，这块专门做了适配：

| 协议端 | 商城表情怎么传 | 表情标记字段 | `summary` 外显 |
|:---|:---|:---|:---|
| **LLBot** | 独立的 `mface` 段，AstrBot 不会把它转成图片组件 | 只有 `subType`（驼峰） | 不发 |
| **NapCat** | 折进普通 `image` 段，连 `sub_type` 键都没有 | 只有 `sub_type`（下划线） | 常为空 |
| **SnowLuma** | 折进普通 `image` 段，且 `sub_type` 是 `0` | 只有 `sub_type` | 一定有 |

对应的处理是：

- **收图**：商城表情直接从 OneBot 原始消息段里读，不依赖 AstrBot 的图片组件（否则 LLBot 的 `mface` 会整段丢失）。判断「这是表情不是普通图」除了看 `sub_type` / `subType` / `summary`，还会看 `emoji_id`、`emoji_package_id`、`key` 这些商城专属字段——SnowLuma 的 `sub_type: 0` 就是靠这一层兜住的。入库时顺带记下 `emoji_id`、表情包 id 和外显名，方便回溯来源。
- **发图**：以「表情」形式发出去时，`summary`、`sub_type`、`subType` 三个键一起写，谁认哪个都能正确渲染成表情，多余的键各家都会忽略。

前提是 OneBot 的 `messageFormat` 用 `array`（默认值）。如果你把它改成了 `string`，原始消息会变成一段 CQ 码字符串，商城表情就读不出来了。

其它平台（Telegram、QQ 官方机器人）按普通图片处理，功能不受影响。QQ 官方机器人没有 OneBot 的表情标记，另有「表情收录模式（QQ_Official）」这个配置项决定收哪些图。

## 和分段回复插件配合

装了 [astrbot_plugin_outputpro_split](https://github.com/Whereis-Alice/astrbot_plugin_outputpro_split) 这类「把一条长回复拆成几条发」的插件时，本插件的表情包默认是**另一条独立消息**，对方看不见它，也就没法按自己的图片 / 表情策略排版。把「自动表情的投递方式」改成 `attach` 即可解决：

| 取值 | 行为 | 适合 |
|:---|:---|:---|
| `separate`（默认） | 表情单独发一条消息，与以往行为完全一致 | 没装分段回复插件，或只想要最稳的兼容性 |
| `attach` | 表情追加到机器人这条回复的消息链末尾 | 想让分段回复插件把文字和表情一起编排 |

`attach` 的代价是选图必须在回复发出前完成，所以回复会稍慢一点。为此有一道超时（默认 10 秒）：超时、选不出图、任何一步失败都会自动回退成 `separate` 异步补发——**回复本身不会被卡住，最坏情况只是表情来晚一点**。另外，这条回复要被转成长图（AstrBot 的文本转图片）时 `attach` 会自动让位，否则挂在链尾的表情会被一起画进图里。

### 那个「兼容路径」开关是干什么的

`outputpro_split` 判断「这张图是表情包」的方式，是看图片路径里有没有 `plugin_stealer` 字样——那是原插件的目录名，本插件换了包名，自然就对不上了。

打开「为分段回复插件生成兼容路径」后，要附加的表情会先硬链接（同盘失败则复制）到一个名字含该字样的兼容目录，再附加进消息链，这样对方就能正确识别成表情。原图和库里记录的路径都不动，兼容目录只保留最近 64 个文件，磁盘占用可以忽略。

这是个权宜之计：更干净的做法是请上游把 `astrbot_plugin_meme_magpie` 也加进它的识别关键字，到那时把这个开关关掉就行。

## WebUI 管理面板

插件详情页点「表情神偷管理面板」进入，分两个区：

- **审核区**：自动收来的图先到这里，可以逐张或批量通过 / 删除，通过前能直接改分类、标签、描述、角色、作品。
- **图库**：按分类 / 作品 / 关键词筛选，四种排序（最常发送 / 最近发送 / 最新入库 / 最旧入库，全走 SQL），支持批量改分类、批量删除、批量设作用域、批量设角色 / 作品、批量修复来源作用域。

另外有：单张上传（可选 AI 自动识别）、批量导入、批量重新识别、识别失败检测、重复图清理、存储维护（扫描并清理失效索引 / 孤立文件 / 缩略图缓存 / 临时文件）、分类管理。

界面有三套主题（自动 / 终端风 / 像素风）和三种语言，选择会记住。

> **注意**：WebUI 里删除一个分类会同时删掉该分类下所有图片文件，操作前想清楚。

## 常见问题

**装了这个插件，原来的 astrbot_plugin_stealer 要卸载吗？**
不必须。两个插件的数据目录、命令前缀、WebUI 路由都不一样，可以共存。但**收图和发图功能会同时触发**，两个插件都开着会重复收图、重复发图。建议迁移完数据后把旧插件的收 / 发开关关掉，或直接卸载。

**迁移会不会弄坏旧插件的数据？**
`apply` 只读旧目录、只往新目录写，旧数据一个字节都不动，随时可以回退。只有 `move` 会移动文件，那才是不可逆的。

**为什么图片收进来了但没标签？**
基本都是视觉模型没配好或调用失败。看一眼 AstrBot 日志里有没有报错，确认「视觉模型」配置项或全局图片描述模型可用。已经入库的无标签图可以用 WebUI 的「批量重新识别」补上。

**批量识别一直 429 怎么办？**
把并发降到 1、RPM 降到 6~10 再试。如果还是 429，说明上游额度已经很紧，只能分批跑——用「数量上限」每次只处理几十张。

**服务器内存很小（1GB 甚至 512MB），批量识别几百张会不会撑爆？**
不会，但并发别开高。识别一张图的峰值内存已经和图片规模脱钩：512 见方 60 帧的动图约 17MB，1920×480 的 120 帧动图约 22MB，4000×4000 的静态图约 45MB（1.3.0 之前这三个数分别是 89MB、331MB、185MB）。批量识别的峰值约等于「单张峰值 × 并发数」，所以小内存机器把「批量识别并发数」留在默认的 2 或调到 1 就行，跑几百张也只是慢一点，不会把内存吃满。另外「以 GIF 格式发送」会在发图时多一次编码，内存紧张时建议关着。

**表情包发得太频繁 / 太少？**
调「表情包发送概率」。发得答非所问就确认「启用发送意图判断」是开着的。

**必须配嵌入模型吗？**
不必须。没有嵌入模型会自动用 BM25 关键词检索，只是语义相近但用词不同的情况会差一些。

**改了描述，搜出来还是旧的内容？**
正常情况下不会——改描述会即时更新语义向量，重启也会按文本指纹补差。如果确实撞上了（历史版本留下的错位向量），跑一次 `/mp rebuild_vectors` 清空重建即可。

**表情包数量上限是多少？会自动删我的图吗？**
默认 `2000` 张，填 `0` 就是不限制；配置项在插件配置页最顶部的「容量与安全」分组里。默认情况下超出上限**只告警不删**，要删得你自己跑 `/mp capacity`，或者打开「容量超限自动清理」。

**表情包无声无息少了几十张？**
先去日志里搜「容量控制」。1.3.0 及更早版本的默认上限只有 100 张，后台每小时巡检一次、超出就删最旧的，日志里只有一行 INFO 很难注意到——从旧插件迁移进来几百张的人尤其容易踩。1.4.0 已经把默认值提到 2000 并改成默认不删。**但升级不会改写你已经存过的配置**，所以还请去配置页最顶部的「容量与安全」分组亲眼看一眼「最大表情包数量」现在是多少，详见[表情库容量上限](#表情库容量上限)。

**这插件会不会把别人的隐私截图收走？**
会——它不认识什么是隐私。所以默认开启了人工审核（自动收来的图先进审核区），并提供 `local` 作用域（只允许在来源群发送）和黑名单。建议保持审核开启，并用「偷表情黑名单」排除敏感群。

**用 LLBot / NapCat / SnowLuma，商城表情收不到？**
先确认 OneBot 的 `messageFormat` 是 `array` 而不是 `string`，插件要读原始消息段才能拿到商城表情。三家协议端本身的差异插件已经处理，细节见[平台与协议端支持](#平台与协议端支持)。

**装了分段回复插件，表情包排版很怪？**
把「自动表情的投递方式」改成 `attach`，必要时再打开「为分段回复插件生成兼容路径」。见[和分段回复插件配合](#和分段回复插件配合)。

## 修了哪些问题

相比上游 `astrbot_plugin_stealer`，这一版顺手修掉了这些：

- **标签统计命令会误删暂存目录，清理命令反而从未生效**：上游的 `clean` 方法丢了定义行，代码全部掉进了上一个方法的函数体里。结果是 `clean` 执行时报 `AttributeError`，而本应只读的 `tag_stats` 每跑一次就会把 `raw` 暂存目录清空（里面可能还有正在排队等识别的图）。现在两个命令已拆开，并加了回归测试锁住。
- **LLM 收图的入库方式记错**：LLM 通过工具收的图，`add_method` 被记成 `auto`（自动偷取），导致统计口径和自动收图混在一起，现在正确记为 `llm`。
- **批量识别失败时留下脏数据**：视觉模型返回了非法分类时，上游只回退分类，却把同一次分析产出的标签和描述留在了库里。现在整份分析结果一起丢弃，避免「分类是兜底的、标签却是乱的」。
- **WebUI 搜索漏字段**：索引兜底分支只搜标签 / 描述 / 场景，搜不到图上文字、角色、作品、原始文件名。现在与 SQL 分支的字段范围对齐。
- **批量导入无限并发**：上游 README 自己写着「高并发警告，请分批次分析」。现在换成可配置并发 + RPM 令牌桶 + 退避重试，不需要人肉分批。
- **内容审核失败时静默放行**：审核模型超时或额度用尽时的行为不可控。现在默认「审核失败即拒收」，需要放行的人可以显式打开「审核异常时放行」。
- **清理了死代码**：删掉了不再被调用的 `steal_image_direct` 分支。

1.2.0 又修了这些（前两条来自上游，后两条是本插件自己的疏漏）：

- **单张识别接口会把明确的错误盖成 500**：临时文件变量在 `try` 内初始化，而 `finally` 要读它。视觉服务没配好、请求体解析失败这类「还没走到初始化就返回」的情况下，`finally` 会抛 `UnboundLocalError`，前端只看到一个 500，看不到「视觉服务不可用」这句真正有用的提示。
- **按「表情」发图时只写了 `summary`**：LLBot 只认驼峰的 `subType`、NapCat / SnowLuma 只认下划线的 `sub_type`，所以有的协议端会把本该是表情的图渲染成普通图片。现在三个键一起写。
- **审核区填的「作品」存不进去**：待审核更新接口的可写字段白名单漏了 `work` 和 `overlay_text`，在审核区填完点保存会被静默丢弃。这是 1.0.0 引入「作品」维度时漏改的地方。
- **重新识别的「建议改分类」会重复提示**：建议分类和当前分类相同、或分类已经在本次改动里时，仍然会出现在建议列表中。

1.3.0 又修了这些：

- **静态 GIF 一律识别失败**：部分上游网关只接受白名单里的图片格式（png / jpeg / webp 等），收到 GIF 会直接返回 `mime type is not supported`。旧逻辑把它当普通失败重试，几次全撞同一堵墙，纯烧额度。现在送图前就把非白名单格式转成 PNG，万一仍被拒会本地转码后再补一次，且这次重试不占用重试预算；「格式不支持」这类必然失败的错误也不再和真正的限流混在一起。
- **识别高帧动图会把内存吃光**：旧实现一次性把最多 60 帧全部解码成全尺寸 RGBA 存在列表里，1920×480 的动图光这一步就要 300MB 以上。现在改成两趟处理——先用 32×32 的缩略指纹挑出变化最大的帧，再只解码选中的 12 帧，贴完立刻释放。峰值内存详见[常见问题](#常见问题)里的内存那条。顺带删掉了 PNG 的 `optimize=True`，它白烧 0.6~0.8 秒只省 12% 体积，是旧版「识别动图会卡一下」的另一个原因。
- **发图时转 GIF 的内存翻倍**：旧代码把每帧的 RGBA 副本和 Pillow 保存时自建的调色板副本同时攥在手里（合计 5 字节/像素）。现在读出一帧就立刻量化，编码完逐帧释放，并给帧数和总像素都加了预算。512 见方 60 帧的动图峰值从 41MB 降到 17MB，画质不变。
- **填了一半的弹窗点到外面就消失**：管理表情、编辑标签这些弹窗，原来点一下窗口外的遮罩或者按 Esc 就直接关掉、退回主页面，刚填的内容全没了。现在只要填过东西，点遮罩和按 Esc 都只会让弹窗抖一下、提示你用「取消」按钮。同时修了拖拽选择文本松手时误关、确认框里按 Esc 穿透到底层弹窗、取消编辑后预览层关不掉这三个问题。
- **批量重新识别弹窗内容溢出面板**：选项一多就把按钮顶出可视区。现在内容区可滚动、操作按钮吸底，打开时自动停在第一个「有货」的处理范围上，0 张的档位置灰不可选。

1.4.0 又修了这些（第一条最要紧，来自上游）：

- **表情包会无声无息地少掉**：上游的存储上限默认只有 100 张，而后台每小时会自动把超出的部分连文件一起删掉，日志里只留一行 INFO。从旧插件迁移进来几百张的人什么都没做就会丢图，而且找不到原因。更坑的是上游文档让你迁移完跑一次 `rebuild_index`，那条命令在重建完成后也会顺手执行同一套清理。现在：默认上限提到 2000、支持填 `0` 不限制、后台默认只告警不删（要自动删得显式打开「容量超限自动清理」）、`rebuild_index` 彻底不再删图、真删的时候日志升级成 WARNING 并列出文件名。详见[表情库容量上限](#表情库容量上限)。
- **孤儿清理可能删掉整个图库**：「文件在磁盘上但数据库里没有记录」这个判断完全依赖数据库读得完整，数据目录没挂载好或被整体移动时，旧逻辑会把所有图当垃圾删掉。现在单次清理超过 20%（且至少 20 个）就只告警不动手。路径比较也做了大小写 / 斜杠归一化——Windows 上 `D:\a\b.png` 和 `d:/a/b.png` 是同一个文件，旧代码会把它当成孤儿。
- **改过描述，搜出来还是旧的**：更新描述时只删掉第一条命中的旧向量，历史遗留的重复向量还留在库里参与检索；删除失败也照样写新向量，于是同一张图同时挂着新旧两份描述。现在一次删干净，删不掉就跳过写入并告警。另外新增了文本指纹（数据库 v8），启动时只重算描述真的变过的条目，从旧版升级不会白烧一遍嵌入额度。
- **WebUI 少显示几张图**：图库列表拿图片哈希当列表 key，同一张图分在两个分类下各存一份时会撞 key，Vue 只渲染其中一张。现在改用文件名。

## 注意事项

- **必须配置视觉模型**，否则识别相关的功能全都不工作。
- WebUI 删除分类会连带删除该分类下的所有图片文件。
- 「最大表情包数量」是会真的删文件的硬上限，调小之前请先看[表情库容量上限](#表情库容量上限)。
- 开启「以 GIF 格式发送」时，每次发图都要把动图重新编码一遍，峰值内存虽有预算封顶（见[发图](#发图)），仍高于直接发原图，内存紧张的机器建议关闭。
- 表情包内容和版权归原作者所有，请遵守所在平台的规则，不要用于传播违规内容。
